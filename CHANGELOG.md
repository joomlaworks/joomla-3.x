# CHANGELOG

## Version 3.17 - unreleased [pending]

### Security fixes
- Installer (for new sites): the check which makes a remote database prove the site is yours (delete a file the installer creates) could be skipped. The database step stored the posted settings before checking them, and the step which writes `configuration.php` and creates the Super User never checked them again, so a request could go straight to it: an exposed, not yet installed site could be installed against a database someone else controls, giving them a Super User account. The step now applies the same checks as the database step before writing anything. Confirmed against the code before the fix (stock Joomla 3 behaves the same).
- Installer: once Joomla was installed, anyone could run the installer again while the `installation` folder was still there, from a new browser, overwriting the live `configuration.php` and creating another Super User (stock Joomla 3 behaviour; Joomla relies on the folder being removed). Now only the browser which installed the site can go on (for the extra languages steps); anyone else gets a page saying Joomla is installed, whose links remove the installer, and every other request is refused. Verified: every view and step from another browser, the installing browser's languages step, and the links removing the folder.
- Installer: fixed the Super User's group being set with an `UPDATE` without a condition when the user's group mapping already existed, which put every user of the site into the Super Users group. The mapping is now replaced for that user only.

### Bug fixes
- Fixed the PDO database drivers (`pdomysql`, `pgsql`) failing to be serialized after running a write query, with "Serialization of 'PDOStatement' is not allowed". The drivers' `__sleep()` left out the `PDO` connection but not the `PDOStatement` the driver keeps from its last query, which stays set after an `INSERT`/`UPDATE`/`DELETE` until the next query. Anything that serializes the driver at that moment failed. The most common case is the callback cache, which serializes the cached callback's object and arguments to build its cache key, so the error depended on what was cached and on whether a write (e.g. an article hits update) had just run. It affected every cache handler, not just Memcached. Statement handles are now left out too (they're temporary and never needed after unserializing), in Joomla's driver and in the bundled FOF library's copy. The `mysqli` driver was not affected.
- Fixed the "MySQL (PDO)" driver (`pdomysql`) returning integer and float columns as PHP `int`/`float` on PHP 8.1 and newer. PHP 8.1 changed PDO MySQL's emulated prepares, which this driver uses, to return native types, while `mysqli` (the default driver) still returns strings. Code written for Joomla 3, core and extensions alike, that compares database values strictly (e.g. `=== '1'` or `in_array('0', $list, true)`) could therefore behave differently depending on the database driver. The driver now sets `PDO::ATTR_STRINGIFY_FETCHES`, restoring strings as on PHP 8.0 and earlier, in Joomla's driver and FOF's copy.
- Fixed "Trying to access array offset on false" warnings in the update finder (`libraries/src/Updater/Updater.php`) when an installed extension's `manifest_cache` is empty, `false` or invalid JSON: its version was read without checking that the cache decoded to an array. It now falls back to an empty version, which is exactly what PHP 7.x and earlier did silently, so the extension is still offered the update as before. Also fixed a related potential crash in the core update's preflight check (`com_admin/script.php`), which called `array_key_exists()` on the decoded core manifest cache; on PHP 8 that throws a `TypeError` if the cache isn't valid JSON. It now aborts gracefully, as intended.
- Fixed the "Little WAF" plugin's cached manifest data (`manifest_cache`) staying empty on sites upgraded to 3.16, so Extensions: Manage showed it without version, date or author. Fresh installs refresh every extension's cache, but updates only refresh the extensions on Joomla's core extension list (`ExtensionHelper::getCoreExtensions()`), which it was missing from. It's now on the list, so the next update fills in its cache. The list also tells Joomla Update's pre-update check to treat it as core rather than as a third-party extension.
- Fixed Extensions: Install Languages permanently showing "The update table is not up to date. Please rebuild your update server table" with no languages listed, even after rebuilding the update sites. The screen finds the list of available translations through the "English (en-GB) Language Pack" package (`pkg_en-GB`). Stock Joomla creates that package's database record in a 3.6.0 data-only migration, which some upgrade paths never ran, so affected sites had the package's files but no record. Rebuilding the update sites couldn't help: it only links update sites to extensions that have a record, and if another language pack (e.g. Spanish) declares the same translations feed, the feed was linked to that pack instead. A new data migration, run on every update and doing nothing on sites that are already fine, recreates the missing record (with the next free ID, in case the stock ID 802 is taken), recreates the "Accredited Joomla! Translations" update site if it's missing, links the two, and points the en-GB language records at the package, as stock Joomla 3.7 does. The update then fills in the package's details as for any core extension.
- Fixed PHP 8.5 "Non-canonical cast" deprecation warnings: the remaining `(boolean)`, `(integer)`, `(double)` and `(binary)` casts (in core, the bundled FOF, PHPMailer, idna_convert and joomla/session libraries, the CodeMirror editor and Smart Search's index drivers) are now `(bool)`, `(int)`, `(float)` and `(string)`. The 3.12 sweep only covered `(boolean)` in part of the codebase.
- Fixed thousands of PHP 8.5 "Using null as an array offset" warnings while Smart Search indexes content without a language (the snowball stemmer used the language as a cache key), and a "Passing null to PDO::quote()" warning when the "MySQL (PDO)" driver escapes a `null` value. The bundled FOF library's `mysqli` and `postgresql` drivers got the same `null` handling as Joomla's own drivers.
- Fixed an "Uninitialized string offset" warning in the command line input parser (`JInputCli`) when an option is followed by an empty argument, e.g. `--name ""`.
- Fixed Global Configuration requiring a database user name, which a database server may not need (and SQLite doesn't use): an empty one can't connect to a server anyway, which saving already checks.
- Fixed the command line hiding the reasons for failures which Joomla reports through its `jerror` log, e.g. the installer's "SQL File not found": `libraries/cms.php` only shows those messages for web requests, so `extension:install` just said "Unable to install extension". The command line now shows them as warnings.
- Fixed PHP 8.4/8.5 deprecation warnings when checking for updates and reading feeds: `xml_set_object()` (deprecated in 8.4) in the update parsers and SimplePie now gives the parser method callables instead, on PHP 8.4 and newer only, so older versions behave exactly as before; `xml_parser_free()`, `curl_close()` and `finfo_close()`, which do nothing since PHP 8.0/8.1 and are deprecated in 8.5, are no longer called on those versions (update parsers, HTTP transport, FOF downloads, reCAPTCHA, SimplePie, upload MIME checks); `socket_set_timeout()` (deprecated in 8.5) is now its identical `stream_set_timeout()` in both FTP clients.
- Fixed PHPMailer's NTLM authentication helper calling `mhash()` (deprecated since PHP 8.1); it now uses `hash('md4', ..., true)`, which gives the same bytes.
- Fixed the LDAP client passing a port to `ldap_connect()`, deprecated since PHP 8.3. On PHP 8.3 and newer the host (or space-separated hosts) and port are now given as `ldap://host:port` URIs; hosts already given as URIs are kept, and older PHP versions are unchanged.
- Fixed PHP 8.5 "Using null as an array offset" warnings while Smart Search indexes items with an empty taxonomy title, e.g. no author name (`helpers/indexer/taxonomy.php` and `result.php`). The value was already stored as an empty string.
- Fixed extension updates losing their download key or other extra query (set for an update site, e.g. by a commercial extension) when the package URL already had a query string: Extensions: Update joined them with a literal `&amp;`, so the server received a parameter named `amp;dlid` instead of `dlid`. Also, when a downloaded update can't be unpacked (e.g. the server sent an error page instead of the package), the download is no longer left in the temporary folder.
- Fixed the "System - Joomla! Update Notification" plugin emailing the Super Users about a pending Joomla update every time it checked for updates: every "Updates Caching" interval of the Installer options (6 hours by default, so 4 emails a day) until the site was updated, and on every page load with the interval set to 0. It now emails once a day, from the new "Email Time" option on (a drop-down of the hours 00:00–23:00, default 10:00, in the time zone of the Global Configuration): the first visit to the site at or after that hour while an update is pending sends the email, and the next one waits until that hour the next day. An update found later in the day is reported on the first visit after it was found. The update check still follows the Installer setting and runs independently; it stores the version it found in the plugin's options, so most page loads decide without querying the database. The times of the last check and the last email are read and written while the table is locked, and only the changed time is written, so a request can't overwrite the other time with an older value. The email's release news link now points to this project's repository instead of joomla.org's announcements, which don't cover Joomla 3.x UTD versions.
- Fixed a fatal error on PHP 8 with the "File" cache handler when a cache folder can't be created (e.g. permissions): the handler passed an empty path to `fopen()`, which PHP 7 only warned about and PHP 8 rejects with a `ValueError`, even with `@`. Caching is now skipped for that group, as on PHP 7.
- Fixed Joomla's database exporters for MySQL writing column defaults, types and extras into XML attributes without escaping, so a default containing `"`, `&` or `<` (e.g. a JSON default) produced invalid XML. They also now export the length of prefix indexes (`Sub_part`).
- Fixed the database importer of the "MySQL (PDO)" driver failing with a fatal error ("Call to undefined method ... xmlToCreate()") when the imported structure has a table which doesn't exist yet. Both MySQL importers also now create prefix indexes with their length (avoiding "Specified key was too long"), `FULLTEXT` indexes as such, and quote the column names of multi-column indexes.

- Fixed the "MySQL (mysqli)" database driver on PHP 8.1 and newer, where `mysqli` throws its own `mysqli_sql_exception` by default. The driver was written for the older behaviour (functions return `false`, and the driver throws Joomla's exceptions), so on PHP 8.1+ a failed query threw `mysqli_sql_exception` instead of `JDatabaseExceptionExecuting`, which the 74 places in core that handle query errors (and extensions doing the same) don't catch, so an expected and handled error became a fatal one. `getErrorNum()` returned 0, and the driver's reconnect after a lost connection ("MySQL server has gone away") never ran. A failed connection also showed MySQL's raw error, including the database user name, on the site's error page. The driver now switches `mysqli`'s exceptions off when it connects, as on PHP 8.0 and earlier, in Joomla's driver and FOF's copy. Verified on PHP 7.4, 8.1 and 8.5: failed queries throw Joomla's exception with the right error number, and a connection killed by the server reconnects transparently.
- Fixed the "MySQL (PDO)" database driver (`pdomysql`) throwing PHP's `PDOException` for failed queries instead of `JDatabaseExceptionExecuting` (on every PHP version), with the same effects as above: error handling in core and extensions was skipped, and a lost connection was never reconnected. Joomla's PDO driver base also had two bugs on that path: checking whether the connection was still alive ran its test query through the same error handling, which came back to the check and ended the request with "Recursion trying to check if connected."; and after reconnecting, the failed query was run again with a statement prepared on the old, dead connection. The check now queries the connection directly, and the query is prepared again on the new connection. Failed queries now report MySQL's error number (e.g. 1146) instead of the first digits of the SQLSTATE code.
- Fixed the "MySQL (PDO)" database driver ignoring a port or socket in the Database Host field. Unlike "MySQL (mysqli)", it passed the field to PDO as it was, so `localhost:/path/to/mysql.sock` silently connected through the default socket (possibly to a different MySQL server), and `host:port` only worked by accident. Both drivers now share the same host parsing (`host`, `host:port`, `[IPv6]:port`, `:port`, `localhost:/path/to/socket`), verified identical to the mysqli driver's for 32 combinations. The installer also accepts `localhost:/path/to/socket` as a local database host, as a socket is always on the same server, instead of asking to verify the site's ownership by deleting a file.
- MySQL 8.0, 8.4 and 9.x work with their default authentication method (`caching_sha2_password`) without changes to `my.cnf`: authentication is handled by PHP's MySQL client, which supports it from PHP 7.4 (and 7.1.16/7.2.4). Verified against MySQL 8.4 on default settings, with both MySQL drivers, over TCP and the local socket, on PHP 7.4, 8.1 and 8.5, including fresh installations with sample data and the first connection after a server restart (when the server has no cached credentials). When a connection fails because of the database user's authentication method, both MySQL drivers now explain why and what to change, instead of only "Could not connect to MySQL server.": a user on `mysql_native_password`, which MySQL 8.4 disables by default and MySQL 9.0 removed (MySQL error 1524); an authentication method the PHP version can't use, e.g. `caching_sha2_password` on old PHP 7.1/7.2 releases or MariaDB's `ed25519`/`PARSEC` (errors 2054, 1251, 2059); and old PHP versions which don't know MySQL 8's default character set.
- Fixed the "PostgreSQL" database driver (PHP's `pgsql` extension) failing every query on PHP 8.1 and newer, so a site, or an installation, couldn't run with it at all. PHP 8.1 returns `PgSql\Connection` and `PgSql\Result` objects instead of resources, and the driver checked for resources (`is_resource()`) before running a query, when checking the connection and when disconnecting. It now accepts both, in Joomla's driver and FOF's copy. Verified against PostgreSQL 18 on PHP 7.4, 8.1 and 8.5.
- Fixed System Information failing with "unrecognized configuration parameter lc_collate" on PostgreSQL 16 and newer, with both PostgreSQL drivers: the drivers read the database's collation with `SHOW LC_COLLATE`, which PostgreSQL 16 removed. They now read it from `pg_database`, which works with every PostgreSQL version (also in FOF's copy).
- Fixed creating users failing with a duplicate key error on PostgreSQL once the users' ID sequence reached the Super User's ID: the installer creates the Super User with a random ID (e.g. 844), which PostgreSQL's sequences don't move past, so the 844th user couldn't be created. The installer now moves the sequence past it, and the 3.17.0 database update fixes existing sites (only ever moving the sequence forward). Other tables' sequences were checked and are correct.
- Fixed lost database connections on PostgreSQL never being reconnected. With the "PostgreSQL" driver, a failed query threw its exception from inside the error handling, before the reconnect check; the check itself used `pg_ping()`, which quietly reconnects and reports success; and reconnecting with `pg_connect()` returns the same dropped connection. The driver now detects a dropped connection by its status and reopens it with `pg_connection_reset()`, restoring its session options (`standard_conforming_strings`, `escape_string_warning`). With "PostgreSQL (PDO)", the reconnect ran the driver's own session setup query instead of the failed one, so the retried query returned nothing. With all PDO drivers, a failed reconnect also crashed while reading the error from the closed connection. Verified on PHP 7.4, 8.1 and 8.5 by terminating the connection on the server mid-request: the query is retried on a new connection and later queries work.
- Fixed PDO database drivers reporting a failed query as "00000, , " when PDO doesn't throw exceptions (the default before PHP 8.0, e.g. "PostgreSQL (PDO)" on PHP 7.4): the error was read from the connection instead of the statement which failed.
- Fixed the installer stopping after its first step on PHP 8.2 and newer when PHP displays errors (common on development servers): its JSON responses created dynamic properties, whose deprecation notices were printed into the response.
- PostgreSQL support verified for the first time in this distribution, against PostgreSQL 18 with both drivers: fresh installations (with sample data) on PHP 8.1 and 8.5, front end and administrator pages, the database structure check, Joomla updates (`core:update --file`, including the 3.17.0 database update and "Restore uninstalled core extensions"), saving content, Smart Search indexing and the command line commands.
- Fixed Joomla's PostgreSQL database exporter leaving out every column default (it read the driver's `Default` as `default`) and all keys and sequences (it asked the driver for them with the `#__` table name, which the driver doesn't know), so the exported structure couldn't recreate a table. It now uses the real table name, reads defaults straight from the catalog (the driver's `getTableColumns()` blanks the defaults of text columns), writes index and sequence names with `#__` like table names, and escapes the values for XML.
- Fixed uninstalling Contacts or News Feeds failing with a duplicate key error ("idx_client_id_parent_id_alias_language"), leaving the component half removed (its tables dropped, its files and menu items still there), on sites installed with sample data after Banners had been uninstalled. The sample data files (all four, in all three database dialects) still linked the three components' "Categories" administrator submenus to com_categories, which an earlier fix had corrected in the main installation file only; uninstalling Banners therefore left its "Categories" submenu behind at the top level, where Contacts' and News Feeds' own "Categories" submenus then collided with it. The sample data now link them to their components (existing sites are corrected on update, by the earlier fix), and uninstalling removes a component's administrator menu items children first, so no submenu is moved up a level on the way.
- Fixed the utf8mb4 conversion of the database (on update or through Extensions: Database > Fix) reporting errors for the tables of uninstalled Banners, Contacts, News Feeds or Smart Search, and not completing: it now skips them, as the update's schema changes already do.
- The database type lists of the installer and Global Configuration are sorted alphabetically.
- Global Configuration refuses to change the database type between MySQL/MariaDB and PostgreSQL too (not only to and from SQLite), as the site's data would stay in the old database, and points to `database:convert`.

### Improvements
- The installer (for new sites) removes the `installation` folder by itself (see also the security fixes above): the final page says it will, and following its "Site" or "Administrator" link (also at the end of the extra languages steps) removes the folder, shows that it was removed and then opens the page. The manual "Remove installation folder" button is gone. Until the folder is removed, anyone who can reach the site can run the installer, which has no login, against it, so it no longer depends on the site admin remembering. The removal is refused unless it's a POST with the form's token, Joomla is installed (a `configuration.php` exists), and the folder is the installer's own, a real folder (not a link) directly in the site's root; nothing in the request chooses what's deleted. PHP's opcache is cleared for the removed scripts. If the removal fails, the page says so and asks to delete the folder manually; the links then work as normal links. Verified in Chrome on PHP 7.4 and 8.5: the folder, `joomla.xml` and `robots.txt.dist` handled, the redirect to the administrator login, and refusals before installation, without the token, with GET, for a symlinked folder and when a file can't be deleted.
- The installer no longer has FTP options. Its FTP step (shown only when `configuration.php` couldn't be written), FTP settings and the FTP layer used to write `configuration.php` are removed; when the file can't be written, the final page shows its contents to save by hand, as it already did when the FTP write failed. New sites get Joomla's FTP settings empty and disabled; Global Configuration still has them for sites which need them.
- The installer (for new sites) has a new design: an app-style layout with a deep blue sidebar (the Joomla! logo as inline SVG, the install steps as a progress track, and the Joomla!/GPL notice at its bottom) and the content beside it, panels, gradient buttons, pill-shaped switches, sample data as cards, a large percentage while installing and a celebratory finish; on smaller screens the sidebar becomes a header and the steps a strip. The installer no longer shows Joomla's version (one less detail for fingerprinting). The HTML is XHTML-style HTML5 (void elements closed, boolean attributes with values), properly nested and indented, including what Joomla's form field layouts output (normalised by the installer: whitespace, named entities as characters); every page and step of an installation parses as well-formed XML. It no longer loads anything from the rest of Joomla: no Bootstrap, jQuery, jQuery Migrate, Chosen or Joomla core scripts (18 files before; now its own stylesheet and script only). Same steps and the same requests as before (apart from the FTP step, removed later in this version). Its stylesheet uses CSS Grid and Flexbox, a light and a dark colour scheme (following the system's), logical properties for right-to-left languages (replacing a separate RTL stylesheet), and works from phone to desktop widths. Its script is plain JavaScript (fetch, data attributes instead of inline handlers, the browser's own form validation on the fields shown), and the template writes its own page head. Sample data choices show their descriptions, the installation shows each task's progress, and messages appear inside the page. Verified in Chrome (headless, through its DevTools protocol) with complete installations on SQLite and PostgreSQL on PHP 7.4 and 8.5: no requests outside the installation folder, no JavaScript errors and no PHP notices with all errors reported; validation, error messages (wrong database password, mismatched passwords), the SQLite fields, the extra languages steps, a right-to-left language (Arabic) and a phone-sized screen.
### New features
- PostgreSQL in the command line database tools. `database:export` and `database:import` work on PostgreSQL (with either driver), keeping each table's columns, defaults, keys and sequences, and moving each sequence past the imported rows; a PostgreSQL site exported and imported again has identical rows, column defaults and indexes. `database:import` also reads files of the other kind of database, translating the structure. `database:convert` moves a site between MySQL/MariaDB, PostgreSQL and SQLite in any direction (`--to=postgresql` or `--to=pgsql`, with `--host`, `--user`, `--password` and `--database`). Between MySQL and PostgreSQL it translates column types (e.g. unsigned integers become wider ones, MySQL's `char` becomes `character varying`, as PostgreSQL pads `character` values with spaces; PostgreSQL's unlimited `text` becomes `mediumtext`), auto-increment columns (`serial`/`bigserial`), keys (prefix lengths where MySQL needs them; no fulltext indexes on PostgreSQL), Joomla's "no date" values (`0000-00-00 00:00:00` on MySQL, `1970-01-01 00:00:00` on PostgreSQL), time zone offsets of PostgreSQL's "with time zone" columns (dropped, keeping the time Joomla stored), booleans and binary data. NOT NULL columns without a default get the empty value MySQL would use, as code written for MySQL leaves such columns out of inserts. The site is taken offline while its database is copied (unless it already was), and put back online with the switch, or with its current database if the conversion fails (verified by forcing a failure part way). After copying and comparing every table's rows, it fixes the new database's structure as Extensions: Database > Fix does (column types and indexes of the core tables, the utf8mb4 conversion record), so the site starts with "Database table structure is up to date". Verified in every direction on copies of real installations: PostgreSQL to MySQL and back (identical rows), PostgreSQL to SQLite, SQLite to PostgreSQL, and a MySQL installation to PostgreSQL, each followed by the database check, front end and administrator pages, and saving content.
- PostgreSQL install and uninstall scripts for Banners, Contacts and News Feeds, which only shipped MySQL ones, so reinstalling them after an uninstall (also through "Restore uninstalled core extensions") failed on PostgreSQL. They're the definitions of the main PostgreSQL installation file. Verified on PostgreSQL 18 and MySQL 8.4: uninstall (tables, files and menu items removed), restore through a Joomla update, the components' pages, and uninstalling again.
- New SQLite database driver ("SQLite (experimental)"), for small to medium sites, development and testing: the whole site in one file, with no database server. It runs Joomla's and extensions' MySQL SQL unchanged, including raw SQL which doesn't use Joomla's query builder and extensions' MySQL install and update scripts, through the bundled "MySQL on SQLite" emulation layer (`libraries/vendor/wordpress/mysql-on-sqlite`, from WordPress's SQLite Database Integration project, GPL-2.0-or-later). The driver reports itself as MySQL 8 to the code, so no SQLite-specific SQL files are needed; it emulates `SHOW`/`DESCRIBE`/`INFORMATION_SCHEMA`, MySQL's case-insensitive comparisons and `ALTER TABLE ... MODIFY` (by rebuilding the table). Needs PHP 7.4 or newer and the PDO SQLite extension with SQLite 3.37.0 or newer; it's only offered where those are available. Verified on a copy of a site with K2, VirtueMart and other extensions (front end, administrator, saving content, installing and updating extensions, Joomla updates) and with a fresh installation.
  - The installer offers it, asking for the database file instead of a server, user and password; it suggests `database/joomla-<random>.sqlite`. A folder inside the site gets `.htaccess` and `web.config` rules which block web access to it, and the random name protects it on servers which ignore those (e.g. nginx); a folder outside the web root is safest. A database file directly in the site's root folder is refused. As SQLite needs no database user or password, the installer always asks to confirm the site is yours (by deleting a file it creates), as it does for remote databases; otherwise anyone who found a newly uploaded, not yet installed site could install it. The file name must end in `.sqlite`, `.sqlite3`, `.db` or `.db3` (a name a web server would run, e.g. `.php`, is refused, since the file holds content anyone can write), and inside the site the folder must hold nothing else (e.g. not `images/`, whose web access the protection rules would block); Global Configuration and `database:convert` apply the same rules.
  - The driver adds MySQL functions the emulation lacks or gets wrong (`IF()`, which always returned its "else" value; Unicode `LOWER()`/`UPPER()`; `FIND_IN_SET()`, `SUBSTRING_INDEX()`, `RIGHT()`, `LPAD()`/`RPAD()`, `UUID()`, `LAST_INSERT_ID()`). The vendored emulation carries five translator fixes, listed in its `PATCHES.md` (`STRAIGHT_JOIN` and other SELECT hints, `GROUP_CONCAT(... SEPARATOR ...)`, parenthesized `UNION` operands, `INSERT ... SELECT` with unaliased values).
  - Joomla's ordering code (`Table::reorder()`) used MySQL user variables, which the emulation can't assign inside expressions; the driver's query class uses the standard `ROW_NUMBER()` window function instead. The update script skips the MySQL-only storage engine check and records the utf8mb4 conversion as done (SQLite stores all text as UTF-8).
  - Global Configuration shows a "Path to Database Folder" option for SQLite, instead of the server, user, password and database name, which SQLite doesn't use. Changing it moves the database: Joomla writes a consistent copy into the new folder (SQLite's `VACUUM INTO`, safe while other requests use the database), checks it, switches the running request to it, saves `configuration.php`, and only then deletes the old file (and the old folder inside the site, when only its protection files are left). If any step fails, the site keeps using the database where it was. Folders inside the site get the same web-access rules as the installer's, and a database there is stored relative to the site's root, so the site can still be moved as a whole; the site's root folder itself and a folder which already has a file of that name are refused. `config:set db=...` on the command line moves the database the same way.
  - System Information (and its text/JSON downloads), the Statistics modules (administrator and site) and the `site:info` command show the database as SQLite with its real version, e.g. "3.46.1 (MySQL 8.0.38 emulation)", instead of the MySQL server the driver reports to the code. The driver's internal name stays `mysqlonsqlite`, as Joomla 3 already has a basic `sqlite` driver with different behaviour.
  - Sessions: the "Database" session handler writes to the database on every page view, which for SQLite means rewriting the database file all the time, even while only browsing. The installer therefore sets SQLite sites to PHP sessions (the "PHP" session handler), and `database:convert --to=sqlite` switches a site from "Database" to PHP sessions, keeping Memcached, Redis or APCu (preferable for performance where available) as they are. Measured on a site's copy: with database sessions, every administrator and front-end page view changed the session table; with PHP sessions, browsing the administrator wrote nothing, and the front end wrote once per new visitor (the session's who's-online record).
  - Known gaps, unused by Joomla core: `DIV`, `TIMESTAMPDIFF()`, `LENGTH()` counting characters instead of bytes, `ADD COLUMN ... AFTER` adding the column at the end. SQLite allows one write at a time, so busy sites with many simultaneous writers should stay on MySQL/MariaDB.
- New `database:convert` command line command, which moves a site's database between MySQL/MariaDB and SQLite, in both directions (`--to=sqlite`, or `--to=mysqli`/`--to=pdomysql` with `--user`, `--password`, `--database`). It copies every table with the site's prefix into the new database, compares each table's number of rows, and only then changes `configuration.php`; the old database is left as it is. A round trip of a whole site's database (MySQL to SQLite and back to MySQL) gave identical rows in every table. Global Configuration refuses to switch between SQLite and the other database types, which would leave the site's data in the old database, and points to this command.
- New command line interface, `cli/joomla.php`, with the command names, arguments and options of the Joomla 4 and later CLI, built on Joomla 3 code with no new dependencies. Run `php cli/joomla.php list` for the commands and `php cli/joomla.php help <command>` for the details of one. Every command also accepts `--format=json`, which prints one JSON document (`command`, `success`, `exitCode`, `data`, `messages`) for scripts and AI agents; `list --format=json` describes every command, argument and option in one call. Exit codes are 0 for success, 1 for failure, 2 for invalid input, 3 when what was asked for doesn't exist and 4 when it's refused (e.g. the last Super User, a protected extension, missing permissions); in JSON, `error` gives the same as a `code` (`failed`, `invalid`, `not_found`, `refused`) with the `message`. PHP notices go to stderr so they never mix with the output. Extensions can add commands through plugins of the new `console` group, by returning command objects (`Joomla\CMS\Console\AbstractCommand`) from the `onGetConsoleCommands` event.
  - Site and configuration: `site:info` (an overview of the site and its environment; not in Joomla 4+), `site:down`, `site:up`, `config:get` (passwords and keys are masked unless `--show-secrets` is given; the option name can hold the wildcards `*` and `?`, e.g. `config:get 'memcached_*'`, which Joomla 4+ doesn't support), `config:list` (all options, or a `--group`; not in Joomla 4+) and `config:set` (which saves through the Global Configuration model, so its checks apply, e.g. the database settings must connect).
  - Users: `user:list` (optionally only users whose username, name or email matches a name filter, e.g. `user:list '*@example.com'`; not in Joomla 4+), `user:add`, `user:reset-password`, `user:addtogroup`, `user:removefromgroup`, `user:delete`, and `user:block`/`user:unblock` (like Users: Manage > Block/Unblock; blocking also ends the user's sessions; not in Joomla 4+). Missing values are asked for at the terminal (passwords without echo); without interaction the options are required. The last active Super User can't be deleted, blocked or lose Super User rights, and a user can't be removed from their last group.
  - Extensions: `extension:list` (optionally only extensions whose name or element matches a name filter, e.g. `extension:list '*k2*'`, also with `--type`; not in Joomla 4+), `extension:install` (`--path` to a package file or folder, or `--url`), `extension:remove`, `extension:enable`, `extension:disable`, `extension:discover`, `extension:discover:list` (with the same name filter), `extension:discover:install`, and `extension:update` (updates one or more extensions by ID, like Extensions: Update, with the updates found by `update:extensions:check`; not in Joomla 4+). Protected core extensions can't be disabled or removed, nor templates used by a default template style.
  - Updates and maintenance: `core:update:check`, `core:update:channel`, `update:extensions:check` (with a `--use-cache` option, not in Joomla 4+, for frequent cron jobs), `update:joomla:remove-old-files`, `cache:clean`, `session:gc`, `session:metadata:gc` and `finder:index`.
  - Updating Joomla: `core:update` downloads the latest version of the update channel, verifies its checksum when the update feed gives one, copies the files over the site (leaving out `installation/`) and then finalises the update (database changes, update script, removal of obsolete files) in a new PHP process, so the new code does it, like the separate requests of Joomla Update. It logs to `joomla_update.php` and records the update in the User Actions Log, like Joomla Update. `--restore-core` reinstalls uninstalled core extensions, like Joomla Update's "Restore uninstalled core extensions" option, `--reinstall` installs the current version's files again when there is no newer one, and `--file` installs a local package (`.zip`, `.tar`, `.tar.gz`/`.tgz` or `.tar.bz2`, also with all files in one top folder, like a GitHub download) instead of the update channel's, e.g. to test a newer or customised build, also with `--restore-core`; all three are additions over Joomla 4+. Packages older than the installed version are refused, as database changes can't be undone. Unlike Joomla 4+, a site with database structure problems is warned about them but still updated, as Joomla Update does, since updates often fix them. Exits with 0 when there is nothing to update.
  - Database: `database:export` writes each table (or `--table`) to an XML file, optionally in a ZIP archive (`--zip`, or `--zip=name.zip` for a custom name, an addition over Joomla 4+), and `database:import` replaces tables from such files (MySQL and MariaDB only). Files are in the format of Joomla 4+'s commands, so files can be moved between the two in both directions; exports also carry each table's exact `CREATE TABLE` statement, which Joomla 4+ ignores and the import uses, so tables come back identical (verified with `CHECKSUM TABLE` across a whole site's database). Rows are read in batches and written to the file as they're read, and the import reads files as a stream, so large tables need little memory. Unlike Joomla 4+'s, the export keeps `FLOAT` values exactly (MySQL prints them with 6 significant digits), keeps carriage returns, base64-encodes binary values, and writes NULLs as valid XML; the import also reads the Joomla 4+ files whose NULLs aren't valid XML. The import asks for confirmation when interactive.
  - `maintenance:database` lists the problems of Extensions: Database, and fixes them with `--fix`.
  - Commands which change things act as a Super User, since whoever runs the command line can already change `configuration.php`. That user exists only in memory, only for the command's duration, and is never stored in a session. The content commands (below) act as a real account instead.
  - Content: `article:list`, `article:get`, `article:create`, `article:update`, `article:publish`, `article:unpublish`, `article:archive`, `article:trash` and `article:delete`; the same for categories (`category:*`, also of other components with `--extension`, e.g. `com_contact`), modules (`module:*`, with their options as JSON, the pages they show on, and the content of Custom modules) and menu items (`menu:list`, `menu:item:*`, linking to an article, a category blog or list, the featured articles, any component page or URL, an alias, a heading or a separator). All additions over Joomla 4+. They save through Joomla's own administrator models and forms, so the text filters of Global Configuration, content plugins, versions, tags, Smart Search and the "same alias" checks apply as in the administrator. They act as a real account: the first active Super User, or the one given with `--as`, whose permissions are checked (create, edit, edit own, edit state, delete), so e.g. an Editor account can write and change articles but not publish them. New items are unpublished unless `--state=published` is given, so they can be checked first. An item someone has open for editing is refused unless `--force` is given, and only trashed items can be deleted, as in the managers. Long texts can be read from a file or the standard input (`--text-file`).
  - `--dry-run`, a new global option: a command reports what it would change (as "Would: ..." lines, and a `plan` list in JSON) and changes nothing. Every command which changes something supports it (also `config:set`, `core:update`, `database:convert`, `extension:install` and the others); commands which only read ignore it, and any command (e.g. from an extension) which doesn't support it refuses to run rather than run for real. `list --format=json` and `help` say which commands only read and which support it.
  - `site:health`: one report of the site's health (PHP version and its security support, PHP extensions, database version, database structure, pending Joomla and extension updates as last checked, debug and error reporting, the installation folder, `configuration.php` permissions, the temporary and logs folders, where a SQLite database is, session and cache handlers, Force HTTPS and Little WAF), each check `ok`, `info`, `warning` or `error` with what to do; `--strict` fails on errors (for monitoring).
  - Logs: `log:list` lists the log files (Global Configuration's logs folder, and PHP's error log when it's a file), and `log:tail` shows the last entries of one, split into their fields, filtered by `--priority`, `--category`, `--grep` and `--since`. Only those files, by name, can be read. `actionlog:list` shows the User Actions Log (who did what and when), filtered by `--user`, `--extension` and `--since`.
  - The User Actions Log records every command run which may have changed the site (not dry runs, nor commands which only read, nor the cache, session and indexing housekeeping of cron jobs), with its arguments and secret values (passwords, keys) left out, as the user `cli`: e.g. "Command line: config:set caching=1", or "MCP: article:create ..." for changes made through the MCP server.
  - `mcp:serve`: an MCP (Model Context Protocol) server on the standard input and output, so AI assistants (e.g. Claude Code or Claude Desktop, also over SSH) can use the commands as tools, each with a JSON Schema of its arguments and options, read-only/destructive hints and the JSON results. It's read-only by default: the assistant can use the commands which only read, and dry runs of the others, but can't change the site. `--allow-write` offers every command; `--allow`/`--deny` narrow them down (e.g. `--allow="article:*,category:*,site:*"`), and `--as` fixes the account the content commands act as, so its permissions apply whatever the assistant asks. Options which would read files on the server (`--text-file` etc.) or reveal secrets (`--show-secrets`) aren't offered. Speaks the protocol versions 2024-11-05 to 2025-11-25. Tested with a scripted client: the handshake, the tool list, calls, refusals in read-only mode, dry runs, unknown tools and methods, `--allow`, `--as` (an Editor account), on PHP 7.4 and 8.5.
  - The content commands, `--dry-run` and the MCP server were tested on SQLite and PostgreSQL 18 sites, on PHP 7.4 and 8.5 with every PHP message reported: a suite of 47 command runs (creating, changing, listing, publishing, trashing and deleting each kind of item, permissions of an Editor account, refusals and missing items), with the site's front end showing the results.
  - Name filters work the same in every command which has one: the wildcards `*` (any characters) and `?` (one character) make a pattern, otherwise the name must match exactly; case is ignored. `list` explains them and ends with practical examples, and `help <group>` (or just the group, e.g. `php cli/joomla.php user`) lists the commands of a group, e.g. `user:*`.
  - Third-party extensions only run in the commands that need them (e.g. content and finder plugins in `finder:index`, user plugins in `user:*`). Their PHP notices go to stderr, so they never mix into a command's output or JSON, and their exceptions and errors make only that command fail, with exit code 1. A broken console plugin can't stop the core commands from working. `finder:index` presents its work as a request for the site's home page (based on the configured Live Site, if any), since content plugins often read the request's server variables, which the command line doesn't have; the old script left them unset, and the URL paths pointing at `/cli`.
  - The command line uses an in-memory session, so commands never touch the session storage. They work with an empty or broken database, e.g. to restore one with `database:import`, and the old `cli/` scripts no longer leave a session row behind on every cron run. `finder:index` (and `finder_indexer.php`) also removes the session row its site application registers, which showed up as a guest in Who's Online.
  - The existing scripts in `cli/` (`finder_indexer.php`, `update_cron.php`, `garbagecron.php`, `sessionGc.php`, `sessionMetadataGc.php`, `deletefiles.php`) still exist and take the same options, so cron jobs keep working, but now run the matching new command. They now exit with a non-zero code when the command fails. `finder_indexer.php --pause` with no value now uses the documented default (dynamic pausing) instead of a fixed 1-second pause, and `garbagecron.php` now also removes the administrator's expired cache, not only the site's.

## Version 3.16 - released October 3rd, 2026
### Security fixes
- Cross-referenced the Joomla 6.1.4/5.4.9 security release (September 2026, 16 items) against this codebase using the real upstream diffs, and backported 10 confirmed-applicable fixes. Several were listed upstream as "Joomla 4.0 and later" but the vulnerable code is present in 3.x:
  - **Unauthorized account creation via `profile.save`:** the frontend profile controller never checked that the caller was logged in. For a guest, the model saved a brand-new, unblocked `JUser`, even with user registration disabled. Guests now get a 403.
  - **Arbitrary directory deletion via cache purge:** Cache Management's delete action accepted group names such as `../../images`, and the file cache only checked that the target path *started with* the cache folder without resolving `..`. Folder deletion now resolves the real path and refuses anything outside the cache folder, and cache file paths reject traversal in the group name. Reproduced first: the old code really deleted a folder outside the cache.
  - **Two XSS filter bypasses in `InputFilter`:** `java&NewLine;script:` (an HTML5-only entity) and the unterminated `java&#10script:` both got through the attribute filter untouched (confirmed by running the real filter). Values are now decoded the way a browser does (HTML5 entity table, before lowercasing, including unterminated numeric references), `&newline;` is a blocked character, and tabs are stripped from attribute values. Done without `mb_chr()` to stay compatible with PHP 7.1. The related upstream "tab in a `data:text/html` URI" bypass was already blocked by this distribution's broader `data:` URI rule.
  - **Tagged items leaking from restricted categories:** tag views, "Tags - Popular" and "Tags - Similar" only checked each item's own access level, not its category's. All three now require an accessible category ("Tags - Similar" also requires a published one).
  - **Content history comparison ACL:** only the first of the two compared versions was access-checked, so a version of an item the user can't edit could be compared against one they can. Both are now checked.
  - **XSS in `JHtml::link()` / `JHtml::iframe()`:** URLs, iframe names and attribute arrays are now escaped (without double-encoding values that are already escaped), and invalid attribute names are dropped.
  - **XSS in the module manager list:** module positions were echoed unescaped in two places.
  - **XSS in the toolbar link button:** in 3.x the URL is written into an inline `onclick` JavaScript string, a worse context than upstream's `href`. It is now JSON-encoded and then attribute-escaped.
  - **Generic image layout attribute names:** the earlier CVE-2026-48953 fix escaped values but still allowed any attribute *name*. Invalid names are now dropped, matching upstream.
  - **SSRF through URL fields:** the news feed URL, both feed modules' URL, the SEF plugin's site domain and the user profile website now only accept `http`/`https`. The Joomla Update custom URL, previously unvalidated, now only accepts `http`/`https`/`ftp`/`ftps`.
- Smaller hardening from the Joomla 6.1.4/5.4.9 release: the Template Manager's file/folder delete actions reject `..` in the target path; the banner tracks CSV export guards against spreadsheet formula injection; `JUri::isInternal()` rejects URLs containing quotes, spaces or angle brackets; the bundled FOF library's TOTP check now compares in constant time (codes passed as integers with lost leading zeros still match, as before); and `php6`/`php9`/`pht` were added to the upload executable-extension lists where missing.
- Cross-referenced the Joomla 6.1.3/5.4.8 security release (August 2026) against this codebase and backported 4 confirmed-applicable fixes: HTTP response header injection via an unescaped filename in the com_banners click-tracking download and com_contact vCard export (a `"` in a banner's filename or a contact's name could break out of the `Content-Disposition` header); missing per-item `core.edit` checks in the com_categories and com_fields batch-copy operations, letting a user with copy access but no edit rights on a specific source item duplicate it anyway, plus a matching component-context validation gap in com_fields' own edit-permission check; `.shtml`/`.shtm`/`.sht`/`.stm` missing from the Template Manager's executable-extension upload blacklist (low practical risk today, since a separate whitelist already excludes them by default, but now matches upstream). Also fixed an unrelated stored-XSS gap found in the same pass: com_contact's default view echoed the contact name, job title, and category title into public-facing schema.org microdata completely unescaped.
- Confirmed not applicable: access-level and edit-task webservice ACLs, and workflow stage changes (3.x has no API application or com_workflow); HTML mail templates (3.x has no mail template system and sends plain-text mail); the MFA bypass via "Remember Me" cookies (in 3.x the two-factor code is checked during login itself, before the cookie can be issued).

### New features & additions
- Added a new system plugin, "Little WAF" (`plg_system_littlewaf`), that filters known attack signatures against abandoned or historically vulnerable third-party extensions at the earliest possible point in the request lifecycle — before routing or any component/plugin runs. Added after confirming real-world active exploitation of an unpatched Sourcerer install (CVE-2026-74253, fixed upstream in Sourcerer 14.0.0). Ships with two filters, each named after and individually toggled for the extension it targets: blocking Sourcerer-style `{source}...{/source}` URL-based PHP injection attempts (verified against a real observed attack pattern), and, as a precautionary measure, Modules Anywhere-style `{module ...}`/`{modulepos ...}` tags (Regular Labs patched a different vulnerability class — SSRF/XSS/restricted-content exposure — in this extension the same week as the Sourcerer fix). More filters will be added over time as similar patterns are identified. The plugin itself is off by default; once enabled, every filter is on by default, since enabling the plugin is itself the explicit opt-in. Its ordering is set far ahead of every other system plugin so an enabled filter always runs first, before page caching or anything else could short-circuit the request. Existing sites get the plugin added (disabled) automatically on update, via the same idempotent DML-migration mechanism used for prior data-only migrations.
- To bring uninstalled core extensions back, Joomla Update's "Reinstall Joomla core files" and "Upload & Update" screens have a new "Restore uninstalled core extensions" option. It reinstalls them through Joomla's own installer, so their database tables, administrator menu items and permissions are recreated. It also restores their default enabled/disabled state, and puts back the default placement of administrator modules (such as the administrator menu) that have none. Regular updates and reinstalls keep uninstalled core extensions removed.
- Joomla Update now checks the site's database type and version before offering an update, using the `<supported_databases>` tag in a new update details file (`docs/extension-db.xml`) that only sites on 3.16 or newer read. Sites below the minimum versions (see "Improvements" below) get a notice instead of the update. Sites on older versions are still offered 3.16 exactly as before, and the requirements apply from their next update onwards.
- Documented database support honestly in the README: MySQL and MariaDB are tested; PostgreSQL and SQL Server are inherited from stock Joomla 3.x and not tested by this project.

### Improvements to existing features
- Joomla Update no longer brings back core extensions the site admin has uninstalled. The update package always contains every core extension, so after uninstalling e.g. Banners, the next update put all its files back. They weren't installed again, but Extensions > Discover offered them for installation, and once Discover had run, every later update showed a "Refresh Manifest Cache failed: ... is not currently installed" warning for them. The update now deletes the re-extracted files of any uninstalled removable core extension, and any leftover "discovered" placeholder for it. This covers every core extension the Extensions Manager lets you uninstall: Banners, Contacts, News Feeds, Search, Smart Search, Content History, Multilingual Associations and Fields (with all their modules and plugins), plus the standalone site and administrator modules, plugins and the Protostar/Isis templates. Each is checked on its own, so partially removed sets are handled correctly. Weblinks was already handled. Extensions that are new to the version being updated from are still added as usual, because their database records are created by the update itself before this check runs. Only what an uninstall itself removes is deleted again, so leftover media folders that an uninstall keeps are left alone.
- Raised the minimum database versions to MySQL 5.5.3 (the first MySQL 5.5 release with `utf8mb4`; every production 5.5 release qualifies), MariaDB 5.5 and PostgreSQL 9.0, all from around 2010. SQL Server stays at 2008 R2, which is from the same period. The installer enforces them, and its messages were updated in all installation languages. Two Serbian translations wrongly said "MySQL" in the PostgreSQL message; corrected.
- Broadened the update channel to match any Joomla 3.x installation, not just this distribution's own 3.10+ lineage — schema migrations go back to Joomla 2.5.0, so earlier stock 3.x sites can safely jump straight to the current version, the same as stock Joomla's own supported upgrade paths.
- Removed the APC (not APCu), Memcache (not Memcached), XCache, and Cache_Lite cache/session drivers. None of the PHP extensions behind APC/Memcache/XCache are installable on PHP 7.1+ (this distribution's minimum supported version); Cache_Lite is an unbundled PEAR package Joomla itself had already marked deprecated with no replacement, whose last release predates any realistic PHP 7 testing. Selecting any of these was already guaranteed non-functional. Sites upgrading from an older release get the leftover files cleaned up automatically. WinCache was considered but kept, since it still has genuine PHP 7.x support (Microsoft continues to maintain it for IIS-hosted PHP). eAccelerator support was already removed by upstream Joomla years ago; only two unused, already-orphaned language entries for it remained, which were also cleaned up.
- Removed the legacy `mysql` database driver (plus its query, iterator, exporter and importer classes, the deprecated `JDatabaseMysql` alias and FOF's equivalents). It relied on PHP's `mysql_*` functions, which were removed in PHP 7, so it couldn't run on any PHP version this distribution supports. Sites still configured with `$dbtype = 'mysql'` are unaffected: Joomla already switches them to the `mysqli` driver automatically. Upgrading sites get the old files removed.
- Added a plain-text copy of the license (`LICENSE.txt`, identical to `LICENSE.md`). It's no longer deleted during updates, and a misspelled `LISENSE.txt` copy that briefly appeared in the repository is removed from upgraded sites.
- The Memcached cache and session driver is no longer labelled "(Experimental)", after fixing the locking bugs that were the only concrete defects found in it (see "Bug fixes" below).

### Bug fixes
- Fixed updates failing with "Table '…_banners' doesn't exist" (MySQL error 1146) on sites that had uninstalled Banners, Contacts, News Feeds or Smart Search, which drop their database tables when uninstalled. The update's database check re-applied old database changes to those deleted tables and crashed. Database changes for the tables of an uninstalled core component are now skipped, both during updates and on Extensions > Manage > Database (which listed the same errors, and whose Fix button failed the same way). Core changes that only mention those tables in their data still run.
- Brought the News Feeds and Smart Search install SQL in line with the current database structure, so restoring them creates up-to-date tables. Smart Search's PostgreSQL install SQL was rebuilt from the main PostgreSQL install script: it was years out of date and contained MySQL-only index syntax, so installing Smart Search from it on PostgreSQL had never worked.
- Uninstalling Banners, Contacts or News Feeds no longer leaves a stray "com_..._categories" entry under Components in the backend menu. The stock Categories sub-entries of these three components were registered to the Categories component instead of their own, so uninstalling the component left them behind. They're now registered to their own component on new installs and corrected on existing sites during the update. Entries already left behind by an earlier uninstall are removed.
- Fixed the update's final cache cleanup doing nothing on sites using the Redis, Memcached, APCu or WinCache cache handlers (it only worked with the File handler). Those sites were left with stale cached data after every update, including the list of installed components, which could hide newly installed or restored components from the administrator menu. Every cache group is now cleared individually, the same way System: Clear Cache's "Delete All" does. If the cache can't be cleared, for example because the Redis or Memcached server can't be reached, the update now shows a warning suggesting to clear it manually instead of failing silently.
- Fixed Joomla Update's handling of the `<supported_databases>` tag in update feeds. Database types were looked up in lower case, while the XML parser reports attribute names in upper case, so any feed using the tag would have stopped every site from being offered the update. (Stock Joomla 3.x bug; it never surfaced because no update feed used the tag.)
- Fixed a dormant versioning bug in the update-site manifest (`docs/extension.xml`) that would have silently stopped this distribution from offering any further updates once a site reached version 3.20.0, with no error or symptom until someone noticed updates had stopped.
- Fixed two real bugs in the update-extraction engine behind "the archive file is corrupt" false positives when manually uploading an update package: it read large chunks of the archive in a single call without verifying it actually got the full amount back (PHP doesn't guarantee that on every storage backend), and it tested the wrong bitflag bit when deciding whether a ZIP entry uses a trailing data descriptor, which could wrongly desync header parsing on perfectly ordinary zips depending on compression settings. A separate, larger issue remains open: zips built with tools that stream file data (e.g. GNOME Files' "Compress" action, or Windows 11 24H2+'s native "Compress to ZIP") use placeholder sizes in the local file header that this parser doesn't yet resolve via the central directory — manual testing with a standard `zip`-created archive is unaffected.
- Fixed real bugs in the Memcached cache driver's internal locking, found while investigating why it's labelled "Experimental": `flush()` never released its internal lock, and `store()`/`remove()`/`clean()` could leave it stuck if interrupted mid-operation. - Swept the codebase for PHP 7.4–8.5 deprecation warnings using a carefully curated set of automated fixes (805 files), on top of several fixes found individually from real production logs (`com_config`'s Global Configuration/Component Options views, the WYSIWYG editor save/display logic, and the menu manager). Every automated fix was individually verified to keep working on PHP 7.1 and up — not just to silence the warning on newer PHP — and the full set was checked against the real codebase before being applied, not just trusted at face value; one rule that looked like a match for earlier work was deliberately excluded because it would have broken reflection-based access to private/protected members on PHP 8.0 and below. All cosmetic (log-noise) fixes with no behavior change; confirmed with a clean lint pass across every changed file.

## Security Patches

In detail, from most to least severe:

**CVE-2026-40383 — Local file inclusion via view layout parameter (High)**
- `libraries/src/MVC/Controller/BaseController::display()` reads the `layout` request parameter through the permissive `string` filter (not `cmd`), and `HtmlView::setLayout()` splits it on `:` and stores the pre-colon segment as the template-override directory with no sanitization. `loadTemplate()` then substitutes that unsanitized string directly into the template search path before `include`-ing whatever `JPath::find()` resolves — allowing path traversal into local file inclusion.
- Fixed by restricting the template-override segment in `HtmlView::setLayout()` to `[A-Za-z0-9_-]` before it's stored, closing the traversal at the source.

**CVE-2026-352212 — SQL injection in com_tags (Moderate, High impact)**
- `components/com_tags/models/tags.php`'s `getListQuery()` concatenated the "all tags" list's order-direction component parameter directly into `$query->order(...)` with no validation. The sibling single-tag model already whitelists the equivalent value against `ASC`/`DESC` — this second model was missed.
- Fixed by adding the same whitelist check before the value reaches the query.

**CVE-2026-48954 — Stored XSS via language overrides (Moderate)**
- Overridden language strings are rendered via `JText::_()` **unescaped** almost everywhere in Joomla core and third-party extensions (by long-standing convention), including inside hardcoded HTML attributes such as `title="<?php echo JText::_('KEY'); ?>"` (a real example: `com_tags`'s admin tag list). A quote character in an override value breaks out of that attribute. `InputFilter` doesn't stop this, since it only sanitizes HTML *tags* found inside the override text — a bare `x" onmouseover="..."` payload has no `<`/`>` for its tag parser to notice. This is a low-effort privilege-escalation path for any account with delegated `com_languages` edit rights short of Super User (e.g. a "Translator" ACL role): plant the payload once, and it fires for any admin who later visits an ordinary screen rendering that string.
- Fixed with a new 3.x-native form rule: `administrator/components/com_languages/models/rules/languageoverridequotes.php` (`JFormRuleLanguageoverridequotes`, following the existing `com_users` `loginuniquefield` rule pattern), wired via `addrulepath`/`validate`/`message` on `administrator/components/com_languages/models/forms/override.xml`'s `override` field, plus a new language string. Rejects `"`/`'` in override text unless the submitting user has `core.admin`.

**CVE-2026-48950 — XSS in com_templates file manager (Moderate) — fixed, broader in 3.x than upstream**
- The `file` GET parameter is base64-encoded and decoded server-side to resolve a template source/image/font file path. `cmd`-filtering the outer base64 string does **not** constrain what the decoded bytes contain — a `cmd`-safe input can still decode to a full `<script>` tag (verified: `base64_decode('PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg')` → `<script>alert(1)</script>`).
- `administrator/components/com_templates/models/template.php` has this exact bug in **three** places — `getSource()`, `getImage()`, and `getFont()` each independently `base64_decode()` the request parameter with zero subsequent filtering — while upstream's own fix only addressed the "source" case. Fixed all 6 corresponding echo sites (file/image/font × 2 each) in `views/template/tmpl/default.php` with `$this->escape()`.

**CVE-2026-48953 — XSS in the generic image output layout (Moderate)**
- `layouts/joomla/html/image.php` only escaped the `src` and `alt` attributes before handing the full attribute array to `ArrayHelper::toString()`, which concatenates every other key (`title`, `class`, `data-*`, etc.) into `key="value"` with no escaping. Not triggered by core's own templates today, but it's a public layout API third-party extensions call directly with arbitrary attributes.
- Fixed by escaping every scalar attribute value in the array before rendering, not just `src`/`alt`.
- Note: advisory listed this as "4.0.0+ only" — the vulnerable file and pattern are identical in 3.x; backported anyway.

**CVE-2026-48952 — XSS in com_installer update list view (Moderate)**
- `administrator/components/com_installer/views/update/tmpl/default.php` echoed `client_translated`, `type_translated`, `current_version`, `version`, `folder_translated`, `install_type`, and `detailsurl` raw — all sourced from third-party extension update XML feeds, which can be malicious or MITM'd. The `infourl` link's `href` attribute was also unescaped (only the link text was).
- Fixed by wrapping all of the above in `$this->escape()`.

**CVE-2026-25901 — XSS in com_associations (Moderate) — additional gap beyond the earlier 3.12 fix**
- `administrator/components/com_associations/views/association/tmpl/edit.php`: a prior session's CVE-2026-21631 fix only escaped 3 of the 8+ dynamic `data-*` attributes on this template's two iframes (`referenceTitle`, `referenceTitleValue`, `targetTitle`). This is a *different* CVE covering the rest: `data-associatedview`, both `data-item` (`typeName`), both `data-id`, both `data-language`, and `data-action` on the target iframe.
- Fixed by escaping all of the above.

**CVE-2026-30894 — XSS in com_contenthistory preview (Moderate)**
- `administrator/components/com_contenthistory/views/preview/tmpl/preview.php` echoed the content-history version note and field values raw.
- Fixed by escaping all three.

**CVE-2026-25900 — XSS in feed modules (Moderate)**
- `modules/mod_feed/tmpl/default.php` and `administrator/modules/mod_feed/tmpl/default.php` echoed feed title, image `src`/`alt`, and item title/link raw or under-escaped (content sourced from external, untrusted RSS feeds). The admin variant's link was worse than upstream's own pre-fix state — it only escaped `&`, not `<`/`>`/`"`.
- Fixed by properly escaping all feed-sourced values (`ENT_QUOTES`) in both files. Feed descriptions deliberately left unescaped, matching upstream — they're treated as trusted HTML by design.

**CVE-2026-30895 — XSS in readmore links (Moderate)**
- `layouts/joomla/content/readmore.php` and `modules/mod_articles_category/tmpl/default.php`: `JHtml::_('string.truncate', $item->title, ...)` defaulted to `$allowHtml = true`, preserving (not stripping) any embedded HTML/script in an article title before echoing the truncated readmore link text.
- Fixed by passing `$allowHtml = false` at all 7 call sites across both files (found via a codebase-wide grep for the vulnerable pattern, since upstream's own fix only covered one of our two affected files under a different template name).

**CVE-2026-48902 — Password/username reset links downgraded to plain HTTP (Low)**
- `components/com_users/models/{reset,remind}.php` built the confirmation link with `$mode = force_ssl == 2 ? 1 : (-1)` — `-1` legacy-maps to `Route::TLS_DISABLE`, forcing `http://` unless "Force SSL: Entire Site" was explicitly enabled, even on sites served entirely over HTTPS via a reverse proxy/CDN. This sent the reset token in cleartext.
- Fixed by changing the fallback from `-1` (force HTTP) to `0` (`Route::TLS_IGNORE` — use the current request's scheme), only forcing HTTPS explicitly when Force SSL is on.

**CVE-2026-48901 — Incorrect cache key construction for InputFilter instances (Low)**
- `libraries/src/Filter/InputFilter::getInstance()` built its instance-cache signature from `($tagsArray, $attrArray, $tagsMethod, $attrMethod, $xssAuto)`, omitting the security-sensitive `$stripUSC` parameter. A caller requesting a filter with `$stripUSC` disabled could silently receive a cached instance created by an earlier caller with it enabled (or vice versa).
- Fixed by adding `$stripUSC` to the cache-key signature.
- Note: also listed as "4.0.0+ only" upstream; the exact same code (with the same bug) is present in 3.x — backported anyway.

**CVE-2026-48948 — Access control bypass in com_contact vCard export (Low)**
- `components/com_contact/views/contact/view.vcf.php` (the `&format=vcf` export) never performed the access-level check that `view.html.php` does, allowing anyone to download the vCard of a contact restricted to a non-Public access level (name, email, phone, address) via a direct URL.
- Fixed by adding the same `$item->access`/`$item->category_access` vs. `getAuthorisedViewLevels()` check used in the HTML view, returning a 403 before building the vCard.

**Already covered by earlier hardening — no new gap:**
- **CVE-2026-48905** (XSS via `data:text/html` URIs in the attribute filter) — blocked via the existing **S-1 (CVE-2025-63082)** hardening in `checkAttribute()` (`libraries/vendor/joomla/filter/src/InputFilter.php`), which rejects *all* `data:` URIs except safe base64 images — a superset that also covers `data:text/html`. Verified against the official upstream test case. (Also hardened `checkAttribute()`/`cleanAttributes()` to fully resolve nested/double-encoded HTML entities before pattern-matching, closing a related bypass class as defense-in-depth.)
- **CVE-2026-48903** (checkAttribute filter code) — the official fix adds `\r` to the whitespace-stripping list in `checkAttribute()`. This codebase already strips `\r` — plus `\v` and `\f`, which the official fix doesn't cover — via the **H-1** hardening pass from a prior release.

- **CVE-2026-48899** (sample data plugins ACL) — 3.x has only the `blog` sampledata plugin; all 3 of its steps already combine `isEnabled()` + `authorise('core.create', ...)` checks, predating this CVE. The other two vulnerable plugins (`multilang`, `testing`) don't exist in 3.x.

(Advisory's own range starts at 5.4.0 and doesn't claim to affect 3.x either.)
- **CVE-2026-35220** (CSRF in admin activation endpoint) — advisory range (6.0.0–6.1.0 only) confirmed accurate; the affected dispatcher architecture doesn't exist in 3.x.

**Not backported from this review round:** 13 further advisories confirmed not applicable — they depend on the Joomla 4.0+ webservices/API layer, com_scheduler, com_workflow, or the 4.2+ MFA redesign, none of which exist in 3.x.

## Functional & Bug Fixes

**Modules set to "Use Global" caching ignored Global Configuration's Cache Time**
- Any module (mod_menu and 25 other core modules) with its Caching option set to "Use Global" actually used whatever value sat in its own, separate "Cache Time" field instead of Global Configuration's Cache Time — and that field ships with (and, due to a related quirk, keeps reverting back to whenever cleared) a default of 900 seconds/15 minutes, so in practice "Use Global" almost always meant a fixed 15-minute refresh, regardless of what Global Configuration was actually set to (e.g. 3 minutes).
- Root cause: every core module's "Caching" field is a simple Use Global/No Caching choice, but the underlying `cache_time` parameter ships with a default value that gets permanently saved onto the module the first time it's saved through the Module Manager (or on fresh install, for default sample modules like the Main Menu) — silently overriding the intended fallback to Global Configuration.
- Fixed centrally in `ModuleHelper::moduleCache()` so "Use Global" now always honors Global Configuration's Cache Time outright, for every core (and any similarly-structured third-party) module — regardless of whatever value happens to be stored in the module's own `cache_time` field. Affected sites are fixed automatically on upgrade — no manual database changes needed.
- Added an explicit "Use custom cache time" option to the Caching field on all 26 core modules that support caching (including mod_whosonline, which now also supports Global/custom caching for the first time), so overriding a single module's cache TTL is now a clear, self-documenting choice rather than an unlabelled number field with no explanation of when it takes effect. The Cache Time field only appears once this option is selected.
- Fixed a follow-up bug from the change above: modules set to "Use custom cache time" were never actually cached at all, on any real page load. The module-caching logic itself was correct, but the site's actual per-module page renderer only ever attempted caching for modules explicitly set to "Use Global", so the new custom option silently fell through to always rendering live. Fixed by correcting that check so any enabled caching mode (not just "Use Global") is honored.

**Added "sort by Author" to Extensions > Manage**
- The Author column was already shown on Extensions > Manage but couldn't be sorted, making it hard to group third-party extensions apart from Joomla core ones (e.g. when auditing a large site for stale/abandoned extensions).
- The column header is now clickable like the others, and "Author" is available in the sort-by dropdown, both ascending and descending.

**Misleading "Refresh Manifest Cache failed" warning on every update**
- Sites that have deliberately removed a stock core extension (e.g. the `protostar` template, or `com_banners`/`mod_banners`) saw a "Refresh Manifest Cache failed: X Extension is not currently installed" warning for each one, on every single future Joomla Update run — even though nothing was actually wrong.
- `administrator/components/com_admin/script.php`'s `updateManifestCaches()` now skips extensions already flagged with `state = -1` before attempting to refresh their manifest cache, instead of re-triggering the same known, non-actionable warning every time.

**beez3/hathor never actually removed from the database on upgrade (GitHub issue #7)**
- On some sites upgrading from an earlier Joomla 3.x release, the removed `beez3` (frontend) and `hathor` (backend) templates remained listed in Extensions → Templates, and clicking either threw a PHP error (`uksort(): Argument #1 ($array) must be of type array, false given`).
- Root cause: the SQL migration that removes their database rows is pure data-cleanup (`UPDATE`/`DELETE`), and Joomla's schema-migration runner only knows how to detect and apply structural (`ALTER TABLE`/`CREATE TABLE`) changes — it silently treats anything else as "nothing to do" while still marking the migration as applied. On an affected site, the leftover row's `manifest_cache` can end up set to the literal string `"false"` on a subsequent update, once the template's files are no longer on disk to read — which is what the PHP error above stems from.
- Fixed by executing this distribution's own data-cleanup migration files directly, before the manifest-cache refresh step runs, on every update — bypassing the schema-migration runner for these files entirely, since it was never designed to run this kind of statement. Written to be safely re-run every time, so sites already affected by this (like the reporter's) will self-heal automatically on their next update — no manual database cleanup needed.

**`lcg_value()` deprecated in PHP 8.4 (GitHub issue #12)**
- `plugins/system/sessiongc/sessiongc.php` used the now-deprecated `lcg_value()` (twice) to implement its "1 in 100 chance" garbage-collection trigger, throwing a deprecation notice on PHP 8.4+.
- Fixed by replacing it with an equivalent-probability check using `random_int()` instead — available since PHP 7.0, not deprecated on any supported version. (The deprecation notice's own suggested replacement, `\Random\Randomizer::getFloat()`, needs PHP 8.2+, which is newer than this distribution's recommended PHP baseline, so it wasn't an option here.)

**Literal `"_QQ_"` text appearing instead of quote marks, throughout the admin UI**
- `_QQ_` is a legacy placeholder Joomla language files used in place of a literal double quote, dating back to a PHP 5.2 `parse_ini_file()` bug — long irrelevant given this distribution's modern PHP floor. It was officially deprecated in Joomla 3.9.0 in favour of a real escaped quote (`\"`), but the fallback that was supposed to convert old `_QQ_` usages back into a real quote at load time only runs in a code path that's essentially never used in practice — so on a normal install, `_QQ_` was rendered completely literally, unconverted. Reported symptom: the "Add Install from Web tab" notice on Extensions > Install (shown whenever the web-installer plugin is missing) displayed literal `"_QQ_"` sequences instead of quotation marks, among other places.
- Found via a repo-wide scan: 80 language files, 1436 occurrences, both in the core English UI and in several bundled non-English installation-language packs. Fixed all of them, converting to the proper `\"` escaped-quote form. Verified every `.ini` file in the repository (477 total, not just the 80 changed) still parses correctly.

**Minimum PHP version compatibility gate was wildly out of date**
- `index.php`, `administrator/index.php`, and `installation/index.php` each define `JOOMLA_MINIMUM_PHP` and use it to show a friendly "Your host needs to use PHP X or higher" message before anything else runs. It was still set to the original stock-Joomla value, `5.3.10`, from over a decade ago — far below what this codebase can actually run on. This distribution's own PHP 8.1-compatibility work added nullable type declarations (`?Type $param`) throughout the codebase, which require PHP 7.1 at minimum — a site on PHP 5.6 or 7.0 wouldn't get the friendly error message at all, since the outdated check let it through, and it would hit a raw, unhandled PHP parse error instead.
- Fixed by raising `JOOMLA_MINIMUM_PHP` to `7.1.0` — the codebase's actual, verified floor — in all three entry points, so unsupported hosts now get a clear, actionable message instead of a blank/broken page.
- Also lowered the update feed's own `<php_minimum>` requirement (which separately controls whether "Update Now" even offers this release) from `7.4.0` to `7.1.0` to match. **PHP 7.4+ remains this distribution's recommended production baseline** — it's broadly available across modern hosting (e.g. AlmaLinux 8 with cPanel, or Ubuntu 22.04+ with Ondřej's PHP repositories) and is where we focus testing — but sites on PHP 7.1–7.3 shouldn't be denied security patches just because they haven't upgraded PHP yet. They'll now see and can install updates same as anyone else.

**Housekeeping: removed `README.txt`, renamed `LICENSE.txt` to `LICENSE.md`**
- `README.txt` was unedited stock upstream Joomla boilerplate, fully superseded by this project's own `README.md`; removed outright.
- `LICENSE.txt` renamed to `LICENSE.md` for consistency with the rest of the project's documentation files.
- Both changes are reflected in the core file manifest, and sites upgrading from an older release will have the old files cleaned up automatically — no manual action needed.

In detail:

- Escaped module chrome attributes in `ModuleHelper::renderModule()` with `htmlspecialchars()` before they are passed to `modChrome_*` template functions, preventing XSS via maliciously crafted module style/attribute parameters (CVE-2024-40747)
- Rejected database identifiers containing null bytes or backslashes in `JDatabaseDriver::quoteNameStr()` — both can be used to break out of identifier quoting and inject arbitrary SQL (CVE-2025-25226)
